# Trazabilidad de tecnologías, lenguajes y zonas de uso — SD-04

**Corte:** 2026-10-11. **Propósito:** localizar cada tecnología de la solución propuesta y contrastarla con el stack informado por el usuario en D-12 y con las plataformas actuales. Este archivo es contexto de trabajo; la fuente editable del subdocumento es [`OSS-Subdocumento4.tex`](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex). La Tabla 4.6 de SD-04 selecciona capacidades, mientras que el Formulario T-11 debe fijar versiones, niveles y cantidades ofertadas. «Seleccionado» indica decisión de arquitectura de la propuesta, no un recurso ya contratado o instalado.

## Zonas de referencia

| Código | Zona física o servicio | Función y certeza |
| :-- | :-- | :-- |
| SIT-01 | 22 tiendas físicas | POS, periféricos y nodo local de la solución nueva en cada tienda. El POS 2014 existe; el nuevo diario y sincronizador son propuestos. |
| CD-01 | Centro de distribución principal | Operación logística. El WMS se **supone** alojado aquí; su servidor y base aún no están inventariados. |
| CD-02 | Centro de distribución de Concepción | Operación logística y carga estructurada por personal; no se presupone un WMS ni un nodo local nuevo. |
| DC-01 | Centro de datos de casa matriz, 140 m² | Sitio existente compartido por Retail y Emisor. Alojar aquí ERP/DTE, núcleo Retail 2009 y crédito 2011 es un **supuesto**, no un inventario confirmado. |
| DC-02 | Sala de respaldo del Cliente, en la misma comuna | Sitio existente cuya capacidad y función real en recuperación se deben levantar. Su enlace con DC-01 es **propuesto**. No se le asigna una réplica de aplicación concreta sin inventario. |
| CLD-01 | Microsoft Azure Chile Central, región primaria | Aplicación, integración, eventos y datos nuevos. Radios separados de Retail, Emisor y plataforma compartida, con concentrador de red. Las cargas críticas se proyectan entre tres zonas de disponibilidad. |
| CLD-02 | Microsoft Azure Brazil South, región de recuperación | Réplicas y recuperación de cargas nuevas. La réplica y residencia de datos del Emisor requieren aprobación jurídica; la activación se ensaya. |
| EXT-01 | Contrapartes y plataformas externas | Marketplace, medios de pago, transportistas, proveedores y, **por supuesto de alojamiento**, comercio electrónico y fidelización. No se conoce la ubicación física de cada proveedor. |

**Fuentes de zonas:** [SD-04, vista de sitios y supuestos](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L330), [Tabla 4.7](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L427), [Tabla 4.8](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L444) y [plataformas actuales](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L215). Una zona lógica de Azure no equivale a un edificio identificable para el Cliente; la residencia de cada servicio y de sus registros debe comprobarse.

## Decisiones que evitan lecturas equivocadas

1. **Kong, Apache Kafka y Grafana** figuran en el [stack informado por el usuario, D-12](contexto_sd-04.md#L32). SD-04 selecciona API Management, Event Hubs y Azure Monitor; mencionar aquellas herramientas en el contexto no acredita su inclusión en la oferta. Google Cloud aparece en SD-04 como alternativa evaluada y descartada, no como segunda nube.
2. La integración entre Retail y Emisor conserva sus datos, identidades y claves separados. X-01 gobierna el cruce previsto de autorización de compra; el intercambio solo se habilita con ficha, contrato y controles aprobados en ambos extremos. [SD-04, separación](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L153) y [seguridad](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L348).
3. Un lote existente no demuestra SFTP, API, formato o servidor concreto. El mapa de las 14 interfaces, las pruebas de conectividad y los contratos decidirán la ubicación final de cada adaptador y el tipo de conexión. [Contexto D-01 y D-02](contexto_sd-04.md#L8), [emplazamiento](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L458).
4. CLD-02 representa recuperación propuesta; la residencia del Emisor, la disponibilidad efectiva de niveles Azure en ambas regiones, el RTO/RPO y la capacidad deben probarse antes de cerrar el despliegue. [ADR-06/07 y Tabla 4.6](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L371), [Tabla 4.8](../../02_Propuesta/latex_final/sd-04/OSS-Subdocumento4.tex#L444).
